## 1. GraphRAG vs RAG vs Agent RAG

### 1.1 التعريفات الجوهرية

**Traditional RAG (الاسترداد التقليدي):**
يُحوّل السؤال إلى embedding، يبحث في قاعدة بيانات vectors عن الـ chunks الأقرب دلالياً، ثم يُمرّر هذه الـ chunks للنموذج كـ context. نقطة ضعفه الأساسية: يجلب نصاً قريباً في المعنى لكنه **عمياء عن العلاقات بين المفاهيم** — لا يعرف أن مفهوم A هو شرط مسبق لمفهوم B.

**GraphRAG (Microsoft Research, 2024):**
يبني أولاً Knowledge Graph من المحتوى النصي (entities + relationships)، ثم عند الاستعلام يجمع بين البحث الدلالي والتنقل عبر الـ Graph. النتائج المُعلنة من Microsoft: دقة 80% مقابل 50% للـ RAG التقليدي (3.4x تحسن على أسئلة "global reasoning"). LazyGraphRAG (نسخة 2024) تفوّقت على جميع الطرق المقارنة في 96/96 اختبار.

**نتيجة مهمة من البحث الأكاديمي (2024):** دراسة على كتاب رياضيات جامعي (477 سؤال/إجابة) وجدت أن GraphRAG يتفوق تحديداً في أسئلة تتطلب ربط مفاهيم متعددة عبر فصول مختلفة — وهو بالضبط ما يحدث في التعليم التدرجي (concepts build on each other).

**Agent RAG (الاسترداد العميل):**
لا يسترد مرة واحدة — بل يُقرّر النموذج *متى* يسترد و*ماذا* يسترد، يُعدّل استراتيجيته بناءً على نتائج وسيطة. يدعم أسئلة متعددة الخطوات. التكلفة أعلى بسبب تعدد الـ calls، لكن الدقة أعلى على المسائل المعقدة.

### 1.2 مقارنة موضوعية للسياق التعليمي

| المعيار | Traditional RAG | GraphRAG | Agent RAG |
|---------|----------------|----------|-----------|
| ربط مفاهيم متعددة | ضعيف | ممتاز | ممتاز |
| تتبع المتطلبات المسبقة | مستحيل | طبيعي | ممكن بتوجيه |
| فهم سؤال "لماذا؟" | ضعيف | جيد | ممتاز |
| فهم سؤال "ما هو؟" | ممتاز | ممتاز | ممتاز |
| تكلفة الإعداد | منخفضة | عالية | متوسطة |
| تكلفة الاستعلام | منخفضة | متوسطة | عالية |
| سرعة الاستجابة | سريع | متوسط | أبطأ |
| مناسبة لأطفال 4-16 | جيدة | ممتازة | ممتازة |

### 1.3 RAG Variants الجديدة (2024-2025)

**HippoRAG / HippoRAG 2 (NeurIPS 2024):**
مستوحى من آلية الذاكرة طويلة الأمد لدى البشر — يجمع Knowledge Graph مع Personalized PageRank. النتائج: يتفوق على RAG التقليدي بـ 20% على أسئلة Multi-hop. الأهم: **HippoRAG 2 أرخص بكثير من GraphRAG** مع نتائج مقاربة — ~1,000 token per query مقابل آلاف الـ tokens في GraphRAG الكامل. أسرع 6-13 مرة من IRCoT.

**RAPTOR (2024):**
يبني هيكلاً هرمياً من المحتوى: يُجمّع النصوص ويُلخّصها بـ LLM، ثم يُكرّر التجميع على مستويات أعلى تجريداً. الميزة: يُجيب على أسئلة "الصورة الكبيرة" أفضل من RAG العادي. العيب: تكلفة بناء الهيكل مرتفعة، يُناسب المحتوى شبه الثابت.

**Modular RAG (2024):**
إطار يُجمّع RAG Components كـ modules قابلة للتبديل: Indexing module، Retrieval module، Re-ranking module، Generation module. يسمح بتحسين كل component بشكل مستقل.

**Self-RAG (2023-2024):**
النموذج يُقرّر هو متى يحتاج للاسترداد، ويُقيّم جودة الـ chunks المُستردة بـ "reflection tokens". معقّد التطبيق، يُناسب حالات الاستفسار البحثي أكثر من الشرح التعليمي.

**RAFT — Retrieval Augmented Fine-Tuning (Berkeley, 2024):**
نهج مختلف: يُدرّب النموذج على التعامل مع "وثائق مُضللة" (distractor documents) ضمن السياق. النتائج: تحسن 35-76% على HotpotQA وTorch Hub في RAG متخصص بمجال. **الملاءمة للتعليم:** مناسب لو تريد نموذجاً متخصصاً يُميّز المحتوى الصحيح من المحتوى الجانبي في كتب دراسية.

## 2. Tools / Function Calling

### 2.1 System Prompt الضخم مقابل Tools — مقارنة التكاليف

**المشكلة مع System Prompt الضخم:**
كل request يُعيد إرسال آلاف الـ tokens من السياق. مثال: 3,000 حرف من محتوى الدرس = ~750 token × $0.01/1K tokens × 10,000 طالب × 5 رسائل/جلسة = **$375/يوم** من سياق الدرس وحده، حتى لو النموذج لم يحتجه في معظم الأسئلة.

**Tools بدلاً من ذلك:**
يُرسَل System Prompt صغير (~200 token) + تعريفات الـ tools (~100-200 token). النموذج يطلب البيانات فقط حين يحتاجها:
- 70% من الأسئلة: النموذج يجيب بدون استدعاء أي tool (أسئلة تشجيعية، عامة)
- 20% من الأسئلة: يستدعي tool واحد (get_concept_explanation)
- 10%: يستدعي tool-chain (get_prerequisites → get_concept → check_mastery)

**الأثر التقريبي:** ينخفض متوسط tokens per request من ~3,500 إلى ~800 — **توفير 77%** على الـ input tokens.

**تحذير أكاديمي:** Tool definitions تُضاف للـ context في كل call — التعريفات المطوّلة تلتهم ما تُوفّره. اجعل tool definitions موجزة ودقيقة (≤ 100 token/tool).

### 2.2 Prompt Caching مع Tools

أنثروبيك تدعم `cache_control: {"type": "ephemeral"}` على:
- System prompt + tool definitions ← يُخزَّن كـ cached block
- التكلفة على cache hit: 10% فقط من سعر الـ input token (توفير 90%)
- TTL: 5 دقائق (أو 1 ساعة بسعر 2x للكتابة)

في تطبيق تعليمي: نفس الطالب يُرسل عدة رسائل في جلسة واحدة → الـ system prompt + tools تُكتَب مرة وتُقرأ من الـ cache في باقي الرسائل.

**أثر مُجمَّع:** إذا دمجنا Tools + Prompt Caching + Semantic Cache:
- التوفير المُقدَّر: 85-92% من تكلفة الـ input tokens مقارنة بالنهج الساذج (inject full lesson content في كل message).

```typescript
  {

  },
  {
    name: "get_student_profile",
    description: "أسلوب تعلم الطالب ونقاط ضعفه (ملخص، ليس محادثات كاملة)",
    parameters: { user_id: string }
  },
  {
    name: "get_related_examples",
    description: "أمثلة من الحياة اليومية لمفهوم معين ومستوى عمري",

  },
  {
    name: "record_signal",

```

### 2.4 Structured Outputs / JSON Mode مع Tools

**المشكلة بدون Structured Outputs:** AI يُعيد نصاً حراً — يتطلب parsing هش وpost-processing. في سياق تعليمي: إجابة تُفسَّر بشكل خاطئ قد تُسجَّل signal غلط في LearningSignals.

**JSON Mode (OpenAI / Gemini) و Tool Use Response (Anthropic):**
عند استخدام tools، Anthropic يُجبر الـ output على مطابقة schema الـ tool — هذا بحدّ ذاته يُوفّر structured output بدون إضافة تعقيد.

**الفائدة في التعليم:**

```typescript
// بدلاً من parse نص حر:
// "الطالب يفهم الـ loops بنسبة 75%"

// tool response مضمون:
{
  "assessment": {
    "concept_id": "loops",
    "mastery_delta": 15,
    "signal_type": "socratic_pass",
    "explanation_quality": "good",
    "follow_up_needed": false
  }
}
```

**الأثر على ذكاوي:** استخدام tool call `record_signal()` بدلاً من parse AI response يضمن أن كل تفاعل يُنتج بيانات موثوقة للـ Data Flywheel — بدون هشاشة parsing.

### 2.5 Parallel vs Sequential Tool Calling

| الحالة | Sequential | Parallel |
|--------|-----------|---------|
| A يعتمد على نتيجة B | مطلوب | لا ينفع |
| جلب concept + mastery معاً | ممكن parallel | الأسرع |
| prerequisite check قبل explanation | sequential ضروري | لا ينفع |
| تسجيل signal + إرسال response | parallel (fire-and-forget) | الأكفأ |

**التوصية:** استخدم parallel tools لجلب البيانات الاستكشافية، وsequential للـ decision chains.

## 3. Memory Architecture

### 3.1 أنواع الذاكرة في AI التعليمي

الأدبيات تُميّز أربعة أنواع ذاكرة في الأنظمة الذكية:

| النوع | الوصف | المثال في ذكاوي |
|-------|-------|----------------|
| **Working Memory** | السياق الحالي (context window) | رسائل الجلسة الحالية |
| **Episodic Memory** | أحداث محددة مع طوابع زمنية | "أجاب أحمد خطأ على سؤال الـ loops 3 مرات الإثنين الماضي" |
| **Semantic Memory** | معرفة مُجرّدة وحقائق | "أحمد يُفضّل التعلم بالأمثلة المرئية" |
| **Procedural Memory** | المهارات والأنماط | كيف يحل أحمد مسائل الـ recursion |

### 3.2 الأدوات الحديثة لإدارة الذاكرة

**Letta (MemGPT 2.0):**
مستوحى من OS memory management: Core Memory (في الـ context دائماً، كـ RAM)، Archival Memory (vector store خارجي، كـ disk)، Recall Memory (تاريخ المحادثة). الـ agent **يُحرّر ذاكرته الخاصة** — يُضيف/يُحذف/يُعدّل حقائق بنفسه. مناسب لـ agents طويلة الأمد (أسابيع/شهور). تمويل: $10M seed (سبتمبر 2024).

**Zep:**
يُخزّن الذاكرة في **temporal knowledge graph** — يعرف *متى* تغيرت المعلومة لا فقط قيمتها الحالية. مثال: "أحمد كان يصعب عليه الـ loops في يناير، وتحسّن في فبراير". مناسب جداً للتتبع الزمني للتعلم.

**Mem0:**
الأكثر شعبية (48K GitHub stars، $24M تمويل حتى أكتوبر 2025). يُستخلص الحقائق تلقائياً من المحادثات ويُخزّنها. متوسط tokens per retrieval call: ~6,956 (بنشماركات LoCoMo 2026).

**DB-backed Memory (المُطبَّق في ذكاوي حالياً):**
StudentInsights كـ JSON في PostgreSQL. بسيط وموثوق. العيب: لا temporal reasoning، لا auto-extraction من المحادثات، يتطلب تحديثاً يدوياً أو كوداً صريحاً.

### 3.3 Deep Knowledge Tracing vs Bayesian Knowledge Tracing

**Bayesian Knowledge Tracing (BKT) — الكلاسيكي:**
نموذج احتمالي بسيط: يُقدّر احتمال إتقان المهارة بناءً على أداء الطالب. أربعة parameters: P(L0) إتقان مبدئي، P(T) احتمال الانتقال للإتقان، P(S) احتمال الخطأ رغم الإتقان، P(G) احتمال الصواب بالتخمين. **الميزة:** قابل للتفسير، سريع، موثوق. **العيب:** يُعاملة كل مهارة بشكل مستقل، لا يُمثّل تعقيد الترابط بين المفاهيم.

**Deep Knowledge Tracing (DKT) — Stanford:**
يستخدم LSTM لتتبع حالة المعرفة عبر تسلسل التفاعلات. AUC = 0.86 على Assistments dataset (+25% على BKT). يُمثّل الترابط الضمني بين المهارات تلقائياً. **العيب:** صندوق أسود، صعب التفسير.

**الأحدث (2024-2025):**
- **AT-DKT:** يُضيف topic features + student base level → دقة أعلى
- **DKT-Forget:** يُضيف نمذجة النسيان (memory decay) — مهم جداً للـ spaced repetition
- **Hybrid Transformer + BKT:** يجمع قوة تسلسل الـ transformer مع قابلية تفسير BKT
- **LLM-based Knowledge Tracing (2024+):** يستخدم LLMs مباشرة لتقدير الإتقان — ناشئ، واعد

**ما يُطبّقه ذكاوي حالياً** هو في جوهره نظام **إشارات بسيط** (SIGNAL_DELTA) مع تجميع وتطبيع — وهو أسرع وأسهل للتطبيق، لكنه أبسط من DKT. المقايضة: precision مقابل simplicity.

### 3.4 "تخزين محادثات كاملة" مقابل "استخلاص حقائق"

| المعيار | تخزين محادثات كاملة | استخلاص حقائق (Insights) |
|---------|--------------------|-----------------------|
| حجم التخزين | يكبر لا نهاية | ثابت نسبياً |
| تكلفة الإدراج في context | عالية جداً (آلاف tokens) | منخفضة (~200 token) |
| الدقة في الإجابة | عالية (سياق كامل) | معتدلة (فقدان تفاصيل) |
| الفائدة من الـ Data Flywheel | محدودة (صعب تحليل) | عالية (قابلة للتحليل الآلي) |
| الحماية وفق COPPA/GDPR | حساسة (محادثات خام) | أقل حساسية |
| مناسبة للطفل 4-16 سنة | ✗ غير مناسب | ✓ الأفضل |

**الخلاصة الأكاديمية:** استخلاص الحقائق هو الأنسب للتعليم — المبدأ المُتّبع في ذكاوي (StudentInsights) صحيح معمارياً.

## 4. Multi-Agent Architecture

### 4.1 Single Agent vs Multi-Agent في التعليم

**Single Agent يكفي عندما:**
- مهمة واضحة، مخرج واحد (شرح مفهوم)
- السياق متاح كاملاً في context window
- زمن الاستجابة حرج (< 2 ثانية)
- الميزانية محدودة

**Multi-Agent يُضيف قيمة عندما:**
- مهام متوازية مستقلة (تقييم Socratic + توليد مثال + تتبع mastery)
- تخصص مختلف لكل agent (Curriculum Agent, Explanation Agent, Assessment Agent)
- إدارة فصل دراسي (20 طالب في وقت واحد)
- مراجعة جودة الإجابة قبل إرسالها

### 4.2 مقارنة Frameworks

| Framework | النموذج | مناسبة للتعليم | التعقيد |
|-----------|---------|---------------|--------|
| **LangGraph** | Graph-based workflow | ممتاز | متوسط-عالي |
| **CrewAI** | Role-based agents | جيد | منخفض |
| **AutoGen (AG2)** | Conversation-driven | جيد للـ research | متوسط |
| **Magentic-One (Microsoft, Nov 2024)** | Orchestrator + specialists | جيد للمهام المعقدة | عالي |

**LangGraph** هو الأنسب لذكاوي لأسباب تقنية:
1. يدعم conditional branching (مهم لـ adaptive learning flow)
2. يتكامل مع Next.js/TypeScript ecosystem
3. يدعم streaming native
4. يُتيح تعريف state machine واضح للـ classroom sessions

**Magentic-One** مثير للاهتمام أكاديمياً: Orchestrator يُخطط + specialists ينفّذون. أداؤه على GAIA وAssistantBench "statistically competitive with SOTA". لكن التكلفة أعلى، والتكامل مع Next.js غير مباشر.

### 4.3 نموذج Multi-Agent مقترح لـ Classroom ذكاوي

```
Classroom Orchestrator (LangGraph State Machine)
├── Curriculum Agent    → "ما الدرس/المفهوم التالي لكل طالب؟"
├── Explanation Agent   → "اشرح المفهوم بأسلوب مناسب لهذا الطالب"
├── Assessment Agent    → "قيّم الإجابة + سجّل signal في LearningSignals"
├── Peer Engine         → "اكتشف فرص Peer Teaching (mastery gap)"
└── Confusion Detector  → "رصد علامات عدم الفهم في الـ real-time stream"
```

**تحذير التكلفة:** Multi-agent يُضاعف الـ AI calls. تصميم سيئ → 5x تكلفة. التصميم الصحيح يُشغّل agents بشكل parallel حيثما أمكن، ويُخفّف إلى Single Agent للمهام البسيطة.

| Claude Opus 4+ | $30-60 | $60-150 | للمهام الاستثنائية فقط |

**الدرس:** الفرق بين الأرخص والأغلى = 300-600x. Tiered strategy ليست رفاهية — هي ضرورة.

### 5.2 Prompt Caching — Anthropic

- التوفير: **90%** على Cached input tokens (تُدفع 10% فقط على hit)
- كتابة الـ cache: 1.25x السعر العادي (5 دقائق TTL) أو 2.0x (1 ساعة TTL)
- الحالة المثالية: System prompt + tool definitions + lesson content في الـ cache
- من أحد المطورين: من $8,000/شهر → $800/شهر بعد تطبيق Prompt Caching

### 5.3 Semantic Cache — معدلات الـ Hit Rate الفعلية

| نوع الـ Cache | Hit Rate المتوقع | ملاحظة |
|-------------|----------------|-------|
| SHA-256 Exact Match | 1-5% | أسئلة الأطفال متنوعة جداً |
| Semantic Cache (threshold 0.85) | 30-40% | أسئلة العموم |
| Semantic Cache (threshold 0.92) | 15-25% | أسئلة تعليمية أقل تكراراً |
| Concept-level Cache | 40-60% | تُخزَّن المفاهيم لا الأسئلة |

**المشكلة الجوهرية في ذكاوي Phase 1:** الـ cache الحالي هو SHA-256 على نص السؤال — هذا exact match بالفعل، وهو مُوثَّق أنه يُنتج hit rate ≈ 1-5% لأسئلة الأطفال التي تأتي بصياغات لا نهائية. (هذا ما وثّقه الفريق في DECISIONS.md بعد التجربة.)

**Concept-level Cache (المتفق عليه في D-001):** بدلاً من hash على السؤال، نُخزّن شرح المفهوم + الـ embeddings للمفاهيم. hit rate المتوقع: 40-60% — لأن 100 طفل يسألون عن "الـ loops" يحصلون كلهم على نفس الشرح المُخصَّص للمفهوم (مع تعديل طفيف حسب المستوى).

### 5.4 Tiered Model Strategy لـ ذكاوي

```
طلب وارد
    ↓
[Layer 1] هل السؤال مُخزَّن في Semantic Cache؟
    → نعم: إجابة فورية (تكلفة = صفر AI)
    ↓ لا
[Layer 2] هل السؤال بسيط (تحية، مديح، سؤال عام)؟
    → نعم: Gemini Flash / Haiku ($0.10-1/M tokens)
    ↓ لا
[Layer 3] هل السؤال يتعلق بمفهوم في الدرس؟
    → نعم: Sonnet مع GraphRAG (context صغير من Graph)
    ↓ لا (سؤال معقد، Socratic dialogue، تقييم)
[Layer 4] Sonnet / Opus + full tool chain
```

### 5.5 Pre-generation للمحتوى الثابت

المحتوى الذي يمكن توليده مسبقاً (offline) بدل real-time:
- شرح كل مفهوم بـ 3 مستويات (مبتدئ، متوسط، متقدم) ← يُخزَّن في ConceptChunks
- 5 أمثلة من الحياة اليومية لكل مفهوم
- 10 أسئلة كويز لكل مفهوم مع إجاباتها
- شرح الأخطاء الشائعة لكل مفهوم

الـ Pre-generation تكون مرة واحدة + كلما أُضيف محتوى جديد. تكلفتها ثابتة، لا تكبر مع المستخدمين.

## 6. ما تفعله أفضل المنصات

### 6.1 Khan Academy — Khanmigo

**المعمارية المُعلنة:**
- مبني على GPT-4o / Azure OpenAI
- **Tool-based:** يجلب context من exercises + hints + solutions قبل كل response
- **No full memory:** لا يتذكر محادثات سابقة بشكل كامل — يستخدم بيانات المنصة (مسيرة الطالب في الكورس)
- يستكشف استخدام Phi-3 (small language models من Microsoft) لتقليل التكلفة وتوسيع الوصول

**الدرس:** حتى Khan Academy — مع ميزانيتها — تتحرك نحو Small Models للحالات الأبسط. والـ Tools على Human-generated content أثبت موثوقيته أكثر من AI hallucination.

### 6.2 Duolingo — Birdbrain

**المعمارية:**
- نظام توصية يختار من مئات التحديات الممكنة لكل جلسة
- يستخدم Half-Life Regression (Spaced Repetition algorithm، نُشر ACL 2016) لتحديد *متى* يُراجَع كل كلمة
- Birdbrain يُحلّل: accuracy + response time + mistake patterns
- Session Generator أُعيدت كتابته بـ Scala: من 750ms → 14ms delivery time
- يعالج **1.25 مليار تمرين يومياً**

**الدرس الأهم:** الـ SRS (Spaced Repetition) يزيد الـ retention بشكل مثبت. ذكاوي لا تُطبّق SRS بعد — كل طالب يتعلم وفق mastery score لحظي فقط، بدون نمذجة النسيان.

### 6.3 Squirrel AI (صينية) — Large Adaptive Model (LAM)

**المعمارية:**
- نظام خاص بهم: LAM (Large Adaptive Model) ≠ LLM
- يُحلّل 300 نقطة معرفية إلى 30,000 مكوّن معرفي nano-level
- 112,718 طالب → 108,435 مسار تعلم مختلف (تقريباً مسار فريد لكل طالب)
- نتائج 2024: دقة من 78% إلى 93%، تحسن في كفاءة التعلم 50%

**الدرس:** الحبيبية الدقيقة (nano-granularity) في المفاهيم هي سر التكيّف الحقيقي. ذكاوي تبدأ بـ Concepts عامة — التوجه نحو micro-concepts سيُحسّن الـ adaptive precision.

### 6.3b Synthesis Tutor (Josh Dahn / ex-SpaceX School)

**الخلفية:** Josh Dahn أسّس مدرسة Ad Astra داخل SpaceX عام 2014 بطلب من Elon Musk. في 2020 أطلق Synthesis Tutor للعموم — تطبيق رياضيات للأطفال (5-11 سنة).

**ما توفّر من معلومات معمارية:**

- يتجنب الاعتماد الكبير على LLMs كـ ChatGPT — يُفضّل تصميماً مخصصاً للتعليم
- يستخدم "micro-assessments" مُدمجة في كل درس لقياس الفهم في الوقت الفعلي
- يشترط إثبات الإتقان قبل الانتقال للمستوى التالي (mastery-gated progression)
- يجمع بين AI للتكيّف ومحتوى بشري محكوم الجودة

**حدود البيانات المتاحة:** لم تنشر Synthesis تفاصيل معمارية تقنية علنية. البحث الحي (2025) لم يُسفر عن وثائق هندسية. ما أعلاه مستخلص من مراجعات المنتج والتصريحات التسويقية.

**الدرس:** النهج الحذر تجاه LLMs كـ "chatbot عام" وتفضيل نظام AI متخصص يتوافق مع ما يبنيه ذكاوي.

### 6.4 Carnegie Learning — MATHia

**المعمارية:**
- ITS مبني على Symbolic AI + Machine Learning Knowledge Tracing
- Fine-grained skill tracking (ليس فقط "فهم الـ loops" بل "فهم الـ while loop في حالة الـ counter")
- APLSE Score: مقياس تقدم مُرتبط إحصائياً بنتائج نهاية العام
- Continuous assessment (لا اختبارات فورية — كل تفاعل هو assessment)

**الدرس:** كل تفاعل = بيانات assessment. ذكاوي تُطبّق هذا جزئياً عبر LearningSignals، لكن fine-grained skill decomposition مفقود.

### 6.5 Age of Learning / ABCmouse

**الخلفية:** منصة للأطفال دون 8 سنوات، تُغطي القراءة والرياضيات والعلوم. من أضخم منصات التعليم الرقمي لما قبل المدرسة في أمريكا.

**المعمارية العامة المُعلنة:**

- محتوى متدرج حسب العمر مع نظام تقدم مرئي (خريطة تعلم)
- تكيّف بسيط: يُعيد المحتوى الذي أخطأ فيه الطفل، ويفتح مستويات جديدة عند إتقان السابق
- تجربة UI مصممة للأطفال 2-8: عناصر كبيرة، صوت توجيهي، لا قراءة مطلوبة

**حدود البيانات المتاحة:** Age of Learning لا تُفصح عن تفاصيل AI architecture. المنتج أكثر تركيزاً على content library وgamification من AI adaptation معقد.

**الدرس لذكاوي:** للفئة 4-8 سنوات، UX يسبق AI — الواجهة المبسّطة والصوت الموجّه يُحدثان أثراً أكبر من دقة التكيّف الخوارزمي.

### 6.6 الدروس المشتركة بين جميع المنصات الناجحة

الأنماط المتكررة عبر Khan Academy وDuolingo وSquirrel AI وCarnegie Learning وSynthesis:

1. **المحتوى البشري أساس — AI فوقه:** كل منصة تبني AI فوق محتوى بشري محكوم الجودة، لا تُولّد المحتوى من العدم
2. **Fine-grained skills:** تجزئة المعرفة لوحدات صغيرة جداً هي المفتاح الأول
3. **Every interaction = data:** كل إجابة صواب/خطأ تُغذّي النموذج
4. **Small models حيث تكفي:** لا أحد يستخدم GPT-4 لتحية المستخدم
5. **Spaced Repetition:** موجود في كل منصة ناجحة — لا يمكن تجاهله

## 7. Vector DB + Knowledge Graph — الدمج الأمثل

### 7.1 pgvector مقابل البدائل

| المعيار | pgvector | Qdrant | Pinecone | Weaviate |
|---------|---------|--------|---------|---------|
| الأداء (99% recall, 50M vectors) | 471 QPS | 41 QPS | — | — |
| Filtered Search | متوسط | ممتاز | جيد | جيد |
| التكامل مع PostgreSQL | طبيعي | منفصل | منفصل | منفصل |
| التكلفة مقابل Pinecone | 40% أرخص | أرخص | baseline | متوسط |
| Self-hosted | ✓ | ✓ | ✗ (SaaS) | ✓ |
| مناسب لـ ≤ 10M vectors | ممتاز | جيد | جيد | جيد |

**القرار لذكاوي:** pgvector هو الخيار الصحيح — نفس قاعدة البيانات PostgreSQL، تكاملة مع Drizzle، لا infra إضافي. عند تجاوز 10M vectors أو الحاجة لـ filtered search متقدم، Qdrant يستحق الاستكشاف.

### 7.2 Neo4j مقابل PostgreSQL للـ Knowledge Graph

| المعيار | Neo4j | PostgreSQL (ConceptEdges) |
|---------|-------|--------------------------|
| Multi-hop traversal | طبيعي وسريع | يتطلب CTE/recursive queries |
| Vector search | يدعمه (مع plugin) | pgvector |
| Temporal graph | مع Graphiti plugin | يتطلب columns إضافية |
| Operational complexity | عالية (DB جديدة) | مفردة (نفس الـ stack) |
| مناسبة لـ early-stage | لا | نعم |
| مناسبة عند scale | نعم | يُعاد تقييمه |

**الخلاصة:** للمرحلة الحالية، PostgreSQL + ConceptEdges هو الخيار الصحيح. Neo4j يستحق الدراسة عندما تتعدى الـ concepts آلاف العقد مع علاقات multi-hop معقدة.

### 7.3 الدمج الأمثل: Graph + Vector

الهجين المُثبَّت في الأدبيات (2025):
```
سؤال الطالب
    ↓
[Vector Search] ابحث عن أقرب ConceptChunks دلالياً
    ↓
[Graph Traversal] توسّع إلى المفاهيم المترابطة (prerequisites, examples, related)
    ↓
[Re-ranking] رتّب النتائج حسب: درجة الصلة × مستوى الطالب × graph distance
    ↓
AI يجيب بـ context مُخصَّص ومُنظَّم
```

هذا بالضبط ما يصفه GraphRAG — والـ Stack الحالي لذكاوي (PostgreSQL + pgvector + ConceptEdges) قادر عليه بإضافة طبقة hybrid search.

### 7.4 RAFT في سياق ذكاوي

RAFT (Retrieval Augmented Fine-Tuning) يُفيد لو أراد الفريق مستقبلاً **fine-tuning نموذج صغير** على المحتوى التعليمي العربي:
- يُدرّب النموذج على التعامل مع "وثائق مُضللة" ضمن السياق
- تحسن 35-76% على domain-specific RAG
- **المتطلب:** dataset كافٍ من أسئلة/إجابات تعليمية عربية — لا يتوفر بعد

## 8. تقييم تصميم ذكاوي الحالي — Phase 1

*هذا القسم مبني على قراءة الكود الفعلي، لا على الوصف الخارجي.*

### 8.1 ما هو ممتاز ✅

**Knowledge Graph (Graph.Service.ts + Schema):**
الـ ConceptEdges مع relationship types (PREREQUISITE_OF, EXAMPLE_OF, RELATED_TO, BUILDS_ON) هي معمارية صحيحة تماماً وتتوافق مع أفضل الممارسات الأكاديمية. GetPrerequisites() و GetUnlocks() هي بالضبط الـ operations الأساسية التي يحتاجها النظام التكيفي.

**Multi-Signal Mastery (Mastery.Service.ts):**
SIGNAL_DELTA مع weighted scoring (quiz 15, socratic 25, practical 20, peer 12) هو نهج مدعوم أكاديمياً. الـ upsert مع SQL-level clamping يضمن consistency. تسجيل كل signal في LearningSignals table = Data Flywheel صحيح.

**الفصل بين StudentMastery وStudentInsights:**
قرار معماري ممتاز — mastery quantitative في جدول منفصل، insights qualitative كـ JSON. يُسهّل التحديث المستقل.

**Mascot.Service.ts — in-process LRU cache:**
تحسين تقني جيد يتجنب DB lookup على كل request. الـ TTL 10 دقائق معقول.

### 8.2 ما يحتاج تطوير ⚠️

**Cache.Service.ts — SHA-256 Hash:**
الكود يستخدم exact hash match — يُطابق فقط إذا كان السؤال حرفياً متطابقاً. في الممارسة العملية، hit rate ≈ 1-5% كما وثّقت التجربة (D-001). **ملاحظة محددة في الكود:**
```typescript
// BumpCacheHit has a bug — يُعيّن HitCount = 1 بدلاً من increment
.set({ HitCount: 1 }) // note: would need SQL increment in production
```
هذا يجعل إحصاءات الـ cache غير موثوقة.

**Mascot.Service.ts — Lesson Content injection:**
```typescript
${Lesson.content.slice(0, 3000)}
```
يُحقن 3000 حرف (~750 token) من محتوى الدرس في كل system prompt. مع Prompt Caching هذا يُخزَّن، لكن مع TTL 10 دقائق فقط (in-process LRU). البديل الأفضل: إزالة الحقن المباشر واستبداله بـ get_lesson_content tool.

**Graph.Service.ts — GetFullGraph:**
يجلب كل المفاهيم وكل الـ edges في call واحد. مقبول في المرحلة الحالية (عشرات المفاهيم)، لكن سيُصبح مشكلة عند مئات أو آلاف المفاهيم.

**غياب Spaced Repetition:**
لا يوجد في الكود أي آلية لـ spacing review based on forgetting curve. StudentMastery يُخزّن LastTested لكن لا يستخدمه لتحديد "متى يُراجَع هذا المفهوم؟" هذه فجوة كبيرة مقارنة بـ Duolingo وCarnegie Learning.

**غياب LLM Tools layer:**
المحتوى يُحقن مباشرة في system prompt. لا يوجد tool call layer بعد — يعني النموذج يحصل على كل الـ context حتى لو لم يحتجه.

### 8.3 ما يجب إعادة التفكير فيه 🔴

**ConceptChunks — الاستخدام الفعلي:**
الـ Schema يتضمن ConceptChunks (مُخصّص لـ RAG)، لكن الـ Mascot يجلب محتوى الدرس الكامل من getLessonById() لا من ConceptChunks. الجدول موجود لكنه غير مُدمَّج في الـ flow الفعلي بعد.

**StudentInsights — التحديث اليدوي:**
InsightRows تُقرأ كـ JSON string، لكن لا يوجد في الكود آلية واضحة *لكيفية* تحديث هذه الـ insights تلقائياً من LearningSignals. هذا يعني Data Flywheel موجود كـ infrastructure لكن المحرك (signal → insight extraction) غير مُشغَّل بعد.

**السؤال:** هل نستخدم `multilingual-e5-large-instruct` (open-source) أم `Cohere embed-v4.0` (API)?
**Trade-offs:**
- e5-large-instruct: مجاني، self-hosted، يتطلب GPU أو inference service
- Cohere: مدفوع، API جاهز، يدعم العربية رسمياً، multimodal
**الجهد:** تقييم + POC.
